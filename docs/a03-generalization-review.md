# A03 泛化能力与硬编码审查

审查日期：2026-10-10（北京时间）。已完整阅读总任务大纲 V1.1 和成员 A 指南，按单管理员、少量轻量服务项目的 P0 范围审查。追踪 `ProjectCreate → generate_plan → call_model → json.loads → Plan`，检查生产模块、调用方、冒烟脚本和 Mock 测试。当前没有 README，未开展部署或完整工作流验收。

## 结论与能力分层

**当前已具备：** 与行业无关的项目输入、真实模型 HTTP 调用、结构及跨字段校验。没有按校园报名/PPT 关键词返回固定计划的逻辑，没有失败时的示例计划替代。无需修改生产提示词或业务函数就能传入新的服务想法。

**实际已验证：** 网页报名、PPT 美化两个场景此前通过真实模型验收；本轮摄影输入在不修改生产提示词、Schema 或业务函数的情况下，也产生过合法、主题相关的计划。因此生产模块不是两个固定案例的计划分发器。但此次摄影有两次失败和一次成功，成功输出也未充分覆盖全部验证目标。

**尚未验证：** 非校园行业、不同语言、极端预算/技能组合、复杂项目、逐字段独立影响、长期稳定性及其他模型供应商。三个校园轻量服务案例不能证明任意行业都适用，更不能证明模型必然正确利用每个输入字段。

## 发现、影响与最小方案

### 1. 冒烟主题检查二选一，按位置选择（已局部修复）

- 原位置：本轮修改前 `smoke_plan.py:27–29` 用 `ppt: bool` 选择 PPT/活动词；`:60` 用 `index == 1` 选择场景。
- 具体影响：第三项摄影案例会按活动报名词检查，正确的摄影计划也可能被误报离题；调整案例顺序同样可能误判。该逻辑只检查测试结果，不返回固定计划，也不影响生产生成。
- 最小方案与实施：先报告问题，再仅将检查词放入各测试案例元数据。当前 `smoke_plan.py:34` 接收检查词，`:52、69` 随对应案例传入。摄影案例移到第一项也能正确检查，回归见 `tests/test_a03.py:326`。
- 没有引入行业模板或生产分支。关键词检查仍仅用于测试筛查，不能替代人工语义核对。

### 2. 超范围判断缺失（未新增业务规则）

- 位置：`app/schemas.py:24`、`app/services/planning.py:32` 接受符合字段限制的任何想法；`app/prompts/plan.txt:1–3` 没有专门要求说明超出预算、技能或验证能力。
- 具体情况：整厂建设等非轻量想法，只要字段合法，也会请求相同计划；JSON 合法不代表现有团队可以执行。HTTP 错误处理无法识别这个问题。
- 最小后续方案：明确仅提供需求验证计划、必须人工审阅；经团队确认后，在通用提示词中要求能力不明或超出技能/预算时，在现有 next_tasks/步骤里解释限制、建议缩小验证范围。无需行业白名单或新 JSON 字段。本轮保持生产提示词不变，未实施。
- 不处理的影响：可能得到结构正确但不可执行的计划。适用性不能从 JSON 成功状态推断。

### 3. 摄影输出主题正确，目标覆盖仍不足（内容质量限制）

- 位置：`app/services/planning.py:27`、`app/schemas.py:83` 校验结构和引用，不校验验证目标语义；实际输出见下节。
- 具体情况：q4 问“预约方式有什么建议”，没有直接询问预约意愿；q3 用“200元以内”作为价格锚点，但输入预算 200 元是创业投入预算，不是有依据的销售定价。
- 最小后续方案：人工核对直接预约意愿题和价格区间。后续可在通用提示词中要求区分投入预算与顾客支付价格、覆盖各验证目标，不需要摄影专用模板。本轮不修补输出或修改生产提示词。
- 不处理的影响：结构和关键词都通过的问卷，也可能不足以回答用户的实际验证问题。
