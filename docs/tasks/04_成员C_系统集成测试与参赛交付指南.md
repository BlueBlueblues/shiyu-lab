# 成员 C：系统集成测试与参赛交付指南

版本：V1.1（按参赛指南修订）｜执行期：2026-10-09～10-15｜全部时间为北京时间

统一依据：[01_项目总任务大纲.md](01_项目总任务大纲.md)。本文任务编号C00～C09，验收编号T01～T14沿用总纲，不自建另一套业务接口或统计口径。

## 1. 你的交付目标

你从第一天参与技术实现，交付可复现启动、自动化验收、备份恢复和真实用户试用证据，最后把同一批可验证成果写入申报材料。

你拥有 `tests/`、`scripts/`、README、测试/试用记录和参赛材料。A负责后端，B负责界面；业务修复可以提交PR给相应负责人复核，不绕过他们再写一套实现。

系统“在A电脑能跑”不够；你要证明另一台设备能启动、未登录的试用者能提交、真实反馈被模型使用、报告的数字与数据库一致。

## 2. 先建立三个隔离环境

| 环境 | 数据 / 模型 | 用途 | 能否当真实证据 |
| --- | --- | --- | --- |
| 自动测试 | 临时SQLite + mock模型；test项目 | 每次提交验证功能和故障分支 | 只作为软件测试证据 |
| 开发样例/录屏预演 | 单独数据库 + test项目；按需真实模型 | 联调、熟悉演示步骤 | 不能当真实需求反馈 |
| 正式试用 | 独立保存的数据库 + real项目 +真实受试者 | 形成真实实验和复盘 | 可以，须留运行与试用记录 |

环境统一配置使用 `DATABASE_PATH`。测试前检查路径，禁止测试清空真实数据库。不要把test回答搬入real项目；如果误混数据，应重建干净真实实验并说明旧数据不可用。

### C01｜在第二台设备复现并写README（约1～2小时；10/10上午）

1. 拉取同一仓库，使用Python 3.11；在自己的新虚拟环境安装A冻结的requirements。
2. README按总纲写准备、配置、启动、管理登录、测试、局域网访问、备份恢复方法。
3. `.env.example`保留占位符；不要为了方便把管理员密码或API Key放进README。
4. 验证 `python -m uvicorn app.main:app --host 127.0.0.1 --port 8000` 可启动， `/health`200。
5. 测试公开问卷时另用未登录的浏览器上下文，防止依赖管理员会话。
6. 检查不同电脑路径、静态文件目录和数据库建目录行为；错误给A可复现记录。

如果Windows下命令不同，在README单列Windows PowerShell和macOS/Linux的激活命令；不让AI假设所有成员都用同一操作系统。

验收：你能在A不手动帮忙的情况下按README启动。此时T13先完成“启动”部分，恢复测试留到C06。

### C02｜接口测试骨架和自动验收（约2～3小时；10/10下午～10/11）

1. `tests/conftest.py`为每个测试分配临时数据库，覆盖LLM调用函数，使用总纲格式的固定plan/review fixture。
2. fixture项目必须 `data_kind=test`，包括single/multiple/text三类题；固定输出不声称来自真实模型。
3. TestClient按A的配置提供管理认证、合法Origin与 `X-Requested-With`；公开提交不传管理员认证。
4. `test_api.py`覆盖项目持久化、权限、草稿发布、问卷校验与UUID幂等。
5. `test_statistics.py`覆盖有可选题未答时的分母、多选、零样本；不要仅断言函数返回自己预先写出的字符串。
6. `test_workflow.py`覆盖模型失败、非法JSON、运行锁释放、报告快照和新回答变旧报告。
7. `scripts/smoke.py`只做可重复的最小验收，默认要求test数据库和项目，不向real实验灌入回答；脚本失败非零退出。

核心测试建议按业务分组，而不是逐个字段写几百个重复用例。核心测试命令为 `python -m pytest tests/test_api.py tests/test_statistics.py tests/test_workflow.py -q`；e2e需要启动服务，按C04单独执行，避免未启动时被一起收集运行。

验收：10/10先能测T01～T03；10/11扩展T04～T07/T12。报错定位到具体请求和差异，不只写“接口坏了”。

### C03｜手机访问、公开提交与已知样本统计（约1～2小时；10/11晚）

1. 和A决定暂用可信局域网还是已有公网环境。不得到10/14才首次尝试部署；官方若必须公网，应提前完成。
2. 局域网时在可信网络按README开放监听，手机使用电脑可达IP/端口，不使用127.0.0.1。设置正确PUBLIC_BASE_URL并检查系统防火墙。
3. 公网时确认HTTPS、管理员保护、数据库持久目录与重启不丢数据；不要将SQLite放临时存储。
4. 未登录管理端的手机访问已发布链接，实际选三类题并提交；确认成功提示和数据库记录。
5. 用test项目验证同UUID同内容返回200、不增数，不同内容返回409；非法选项/必答缺失422。
6. 用固定样本检查statistics，而不是用模型估算百分比。

T07的最小手算样本（全属test数据）：

| 回答 | 必答单选q1 | 可选多选q4 | 可选文字q3 |
| --- | --- | --- | --- |
| R1 | o1 | o1、o2 | 第一条文字 |
| R2 | o2 | o1 | 未答 |
| R3 | o1 | o2 | 第二条文字 |
| R4 | o2 | 未答 | 未答 |

应得：response_count=4；q1 answered_count=4，两个选项各50%；q4 answered_count=3，o1/o2各2次，各66.67%，合计133.34%；q3 answered_count=2。所有未选择选项输出0次；零回答各题percentage=null。

验收：手机可独立提交，T05～T07有记录。公开页不展示其他人的原始回答；管理端未认证读数据401。

### C04｜完整浏览器测试与真实模型冒烟（约2～3小时；10/12上午）

1. Playwright使用独立test数据库与mock模型，先启动服务器再运行 `python -m pytest tests/e2e -q`。
2. 一条浏览器测试完成：创建项目→生成→编辑保存→人工发布→复制公开问卷→独立未登录上下文填写→管理统计→复盘→下载Markdown。
3. 管理浏览器上下文配置HTTP Basic；公开上下文不配置。使用B的data-testid，不依赖页面布局或AI文案逐字匹配。
4. 失败保存截图与必要日志，路径注明测试时间和代码commit。
5. 真实模型冒烟另做：至少一次真实计划和一次真实复盘，记录项目/experiment/run_id、供应商/模型、时间、成功/失败、耗时。
6. 真实模型冒烟可以用test项目，它证明模型集成，不能替代真实用户试用；真实反馈必须在C05完成。
7. 验证零反馈复盘、生成报告期间新增回答、重新复盘、服务中断重启的行为。

故障测试：mock模型超时/非法JSON后，旧成果保持、锁释放；同项目并发请求409；中断的running启动后failed/INTERRUPTED。没有自动重试时，点击重试应有一个新的run_id。

验收：T08～T11通过，一条完整流程在浏览器中实际完成。模型内容是否可信还需人工检查，自动测试不能证明全部商业判断正确。

### C05｜组织真实试用与记录证据（约2～3小时；10/12～13）

1. 先冻结一个real实验的题目并由A/B检查，确认没有预置测试回答。
2. 让参与者在自己的设备打开服务页/问卷，尽量独立操作；需要你帮助时记录人工干预。
3. 不替参与者填写。每位受试者实际提交一次，用匿名participant_code在试用记录里对应会话。
4. 记录每次受控提交尝试、成功/失败、页面问题、是否有组织经验和短评价；不把重复点击误当多个独立用户。
5. 试用结束核对数据库有效回答份数与受控会话记录；重复重试不新增回答。公开链接若有无法核实的提交，就分别汇报参与人数与回答份数。
6. 触发一次读取真实数据的复盘，记录report_id、run_id、response_count、cutoff_response_id和生成时间。
7. 三人一起检查模型结论是否对应证据；小样本只作为探索性结果，不说商业成功。
8. 截图/材料隐去任何意外填入的个人信息；原始数据限制访问，删除请求由团队处理。

试用表固定为 `docs/user-test-log.csv`，字段：`participant_code,has_organizing_experience,session_time,attempt_count,success_count,issue,feedback_note`。如果备注含身份信息，先脱敏再提交Git。

| 指标 | 计算来源 | 汇报注意事项 |
| --- | --- | --- |
| 实际参与人数 | 匿名试用会话去重 | 不是数据库回答数量 |
| 有效回答份数 | 当前real实验数据库 | 不把test回答计入 |
| 提交成功率 | 受控试用成功请求次数 / 已记录尝试次数 | 标明仅受控试用范围；没有尝试记录则未测 |
| Agent耗时 | run/tool开始与结束 | 计划与复盘分别报告 |
| 模型调用次数 | llm_client实际HTTP调用日志 | 不能把工具次数当调用次数 |
| 人工干预次数 | 人工记录 | 事先定义一次干预，如重试/改文案/帮助操作 |
| 用户评价与问题 | 实际反馈/观察 | 不补写不存在的满意度 |

验收：至少一轮真实用户实验，有数据库、统计、复盘和过程证据；招募未达5～6人时如实说明实际样本及局限。

### C07｜作品介绍与材料统稿（10/13开始整理，10/14完成）

作品介绍综合第5页赛道内容和第7页统一清单，按以下顺序覆盖：

2. 教育痛点、应用场景、目标用户：大学生创业实践缺少低成本实证工具，社团服务提供实际场景；不编造教学效果。
3. 核心功能与输入→计划/工具→人工发布→真实反馈→统计/复盘过程。

5. OPC实践：实际投入/成本、小团队分工、AI执行、快速验证、下一轮行动。
6. 技术创新点与应用价值，用已实现机制说明，不仅罗列“用了大模型”。
7. 应用成效：真实有效回答、实际参与人数、耗时与失败记录、报告证据。

按总纲第1.3节通用评分20/25/20/25/10及赛道关注重点检查材料。实施显著性重在真实试点和可量化结果；可选用30～45分钟记录同一个简单任务的人工准备耗时与Agent耗时/人工审核耗时作探索性对比。不够时间就不做，不宣称未经测量的提效比例，也不声称一次对比代表普遍效果。

汇总 `docs/technology-sources.md`：A提供模型、供应商、依赖/许可、AI编程工具及用途；B提供素材、字体、图标、模板来源。填来源链接、使用方式、许可/使用条件和是否进入交付物；外部调研资料也标来源。提交支撑材料前脱敏，避免真实反馈个人信息被公益宣传公开。

图表只用真实统计，架构图准确描述已实现模块；服务页截图不能冒充已交付活动报名系统。材料里的“5～6位”“耗时下降XX%”“成交首单”等必须有实际证据，否则改为目标、未测或删除。

A审技术事实与日志，B审页面和功能；C审数据口径及官方格式。表格和截图来自同一次实验快照，避免报告5份而截图8份却没有说明时间差。

### C08｜演示录制与上传预检（10/14）

官方第7页要求MP4、总长≤10分钟、文件≤500MB，概述/核心/总结分别≤2/6/2分钟。团队目标8分钟，按下表合并为三段；不能只满足总时长而超出某一段。

| 段落 | 约时长 | 画面 / 证据 |
| --- | --- | --- |
| 概述 | 1分钟（上限2） | 大学生创业实践痛点、目标用户与服务案例 |
| 核心场景演示 | 6分钟（上限6） | 创建/工具2分钟、发布/实际提交2分钟、真实实验/统计/复盘2分钟；剪辑时给6分钟上限留余量 |
| 效果总结 | 1分钟（上限2） | 真实成效、OPC体现、下一轮行动与局限 |

新建演示项目用test标识，避免录屏者自己的回答混入真实需求样本。已完成真实实验和现场操作分清楚时间，不声称现场刚获得全部真实反馈。

若当时模型服务故障，可展示带时间和run_id的已完成真实记录，并说明当前请求不可用；不要把缓存包装成实时生成。

录制前关闭个人消息弹窗/终端敏感内容；检查麦克风、文字可读性、PDF可打开、视频可播放；核对MP4≤500MB与三段时长。支撑材料按≤100MB控制。提前尝试附件预检或保存草稿，确认是否会直接提交再操作。截止后不接受替换，不能计划提交完再补视频或修扫描件。

验收：三人从头观看一次，所有数字和功能可核验。A/B提出修正当天完成，10/14晚全部材料就绪。

## 4. 错误报告的统一写法

每次问题写入共享任务记录或Issue，最少包含：

```text
编号：BUG-xxx；严重度：S0/S1/S2/S3
```
