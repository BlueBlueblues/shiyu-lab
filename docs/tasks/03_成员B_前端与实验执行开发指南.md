# 成员 B：前端与实验执行开发指南

版本：V1.1（按参赛指南修订）｜执行期：2026-10-09～10-15｜全部时间为北京时间

统一依据：[01_项目总任务大纲.md](01_项目总任务大纲.md)。本文任务编号B00～B08。请先读总纲第6～8节，里面的路由、字段和状态不能自行改名。

## 1. 你的交付目标

让用户能从页面完成创建、查看AI计划、检查实验草稿、发布、分享、填写问卷、查看统计和下载报告。每个可操作按钮都对接真实后端，刷新后结果仍在。

你负责 `app/templates/` 和 `app/static/`。A负责全部路由与数据库；你提出模板名和context需求，A接线。C负责测试与复现；你给C稳定的DOM标识和操作说明。

不另建React/Vue工程，不写第二套API，不把调查回答放localStorage冒充数据库，不让AI生成的HTML成为可执行代码。localStorage只可保存本次提交UUID和成功标记等客户端状态。

## 2. 最小页面地图

## 4. 按顺序完成的任务

### B00｜今晚确定最小布局（30分钟）

画出工作台的四个区域：项目信息、验证计划与实验、反馈统计、运行记录与复盘。确认项目列表/创建/工作台先做，服务页和问卷明天再接。

把模板名和期望context发给A；不要同时设计几十个页面。给C一条用户操作路线，方便提前写验收流程。

### B01｜基础样式与统一请求封装（约1～2小时；10/10上午）

1. `base.html`统一页面标题、导航、内容区域；`app.css`保证320～430px手机宽度不横向溢出。
2. `app.js`封装一个JSON请求函数，读取 `data` 或 `error`，处理401、422、502、504与网络失败。
3. 每次提交都显示“处理中”，禁用重复点击；结束后恢复可用状态。
4. 管理请求超时预算可设70秒，超过后先查询running日志；不要立即自动重复触发模型。
5. 展示模型内容和反馈使用Jinja转义或JS `textContent`；不用 `innerHTML`拼接外部文本。

验收：错误不会被当作成功；一个管理接口401给出重新登录提示；页面console无严重错误。

### B02｜项目创建与列表（约2小时；10/10中午）

1. 创建页逐一对应总纲字段，预算用数字输入、默认100；验证目标给示例placeholder，不当作已填写结果。
2. `data_kind`明确标为“真实实验 / 测试样例”；不把模拟演示数据标为real。
3. 提交 `POST /api/projects`，读取 `data.project_id`，跳转 `/projects/{project_id}`。
4. 422根据fields显示对应输入错误，保留用户已填内容。
5. 列表显示name、status、data_kind、created_at，无项目时提供创建入口。
6. 用户预算为0可提交；必填文本去空格后为空不能提交。

验收：创建成功后刷新列表/重启服务仍显示项目。不要用localStorage列表绕过A的数据库。

### B03｜工作台、AI计划和运行状态（约2～3小时；10/10下午～晚）

1. 详情读取 `GET /api/projects/{project_id}`；固定消费 `project,plan,experiment,latest_report_meta,running_run_id`。
2. draft显示“生成验证方案与草稿”；planned显示计划、编辑、预览、发布；collecting显示链接、统计、复盘；reviewed显示最新报告。
3. “生成”调用plan接口。planned重新生成前弹窗提示“将替换当前未发布草稿”；发布后禁用。
4. 模型请求进行时显示等待说明、禁用生成/发布/复盘按钮；每2～3秒查询runs，拿到run_id后查详情，结束/离页时停止轮询。
5. 日志显示工具真实名称的中文映射、开始/结束时间、status、结果引用、错误；不预先渲染假成功时间线。
6. 状态依据后端数据，刷新可恢复；运行失败保留已有成果和错误信息，提供手动重试。
7. 显示计划中的痛点、价值、3条假设、执行步骤和下一步任务；醒目标明这些是待验证假设。

| tool_name | 页面显示 |
| --- | --- |
| `make_validation_plan` | 制定验证计划 |
| `create_experiment` | 创建实验草稿 |
| `analyze_experiment` | 读取反馈并复盘 |

验收：A真实模型生成后页面显示数据库结果；刷新和失败重试行为正确；C可以看到实际日志。

### B04｜草稿编辑、预览与发布（约2～3小时；10/11上午）

1. 使用实验GET填充landing与questions；页面不需要问卷设计器。
2. landing只编辑title、summary、target_users、value_proposition、features和disclaimer；features使用简单多行输入，不做拖拽。
3. questions只编辑title、选项label和required；不提供新增/删题、改ID、改题型或增删选项按钮。
4. 保留原ID、type和options结构，PATCH提交完整 `landing,questions`。
5. 提醒人工检查措辞：不承诺不存在的服务，不暗示正确答案，不把“愿意了解”写成“愿意付费”。
6. 预览复用service/survey模板，标明“草稿预览，不能提交”。
7. 发布前确认已保存并看过预览；调用publish接口，显示实际service_url/survey_url和发布时间。
8. 发布后编辑入口只读；如果旧页面仍试图保存，409解释为“已发布，若要改题请创建下一轮项目”。

验收：编辑后重开内容保持；未发布公开URL不可访问；发布后可访问且不能改题。发布动作不能在生成计划完成后自动触发。

### B05｜服务展示页与动态问卷（约3～4小时；10/11下午）

服务页按配置展示，CTA连接同token的survey；介绍清楚目前处于需求验证。不要加“已有多少客户”“已成交”等虚构数字。

问卷逐题渲染：

| type | 控件 | 提交值 | required的前端检查 |
| --- | --- | --- | --- |
| `single` | 同题同name的radio | option_id字符串 | 必须选1项 |
| `multiple` | checkbox组 | option_id字符串数组 | 至少选1项 |
| `text` | textarea | 字符串 | 去空格后非空 |

具体步骤：

1. label与控件绑定，使用fieldset/legend区分题组；不要把选项label当作选项ID。
2. 显示必答标记、简答最多1000字符；可选未答字段从answers中省略。
3. 显示简短用途/自愿参与/删除联系说明，勾选同意才可提交；不收集手机号、姓名、学号。
4. 本次填写开始时生成UUID，按token保存当前提交ID；发送 `client_submission_id,consent,answers`。
5. 点击提交时冻结本次payload；网络失败时重发同一UUID和同一payload。若用户改答案，则新建一次提交ID并提醒其重新提交含义，避免409被误解。
6. 请求中禁用按钮；首次201或重放200均显示成功；返回duplicate=true时不要显示“新增了另一条回答”。
7. 失败保留已填答案并显示可读信息；422定位到题；409说明本次ID已用于不同内容，不自动反复重试。
8. 成功后显示收条/时间并禁用再次点击；刷新若有本地成功标记则显示已提交提示。该标记只是避免重复操作，不是独立用户证明。
9. 草稿预览完全禁用提交；正式问卷不要求管理身份。

验收：C用未登录管理端的手机完成单选/多选/简答；数据库多一条实际记录；刷新统计一致。网络失败后重放不重复入库。

### B06｜统计、原始文字和报告（约2～3小时；10/11晚～10/12上午）

1. 统计读statistics接口，显示“有效回答N份”，不自动称“独立用户N人”。
2. 每题展示answered_count；选择题显示label、count、percentage。null显示暂无数据。
3. 多选旁标明“按该题有效作答份数计算，可多选，百分比总和可能超过100%”。
4. 用列表/表格显示即可，P0不要求图表。原始文字通过管理responses/统计texts展示并转义。
5. 复盘按钮调用review接口；只在发布后可用，0回答仍可点击并提示将主要说明证据不足。
6. 报告展示保存的statistics快照和review，不拿当前统计替换旧报告中的数字。
7. 显示报告时间、response_count、real/test与stale。stale时标明“已有新反馈，本报告使用N份回答，可重新复盘”。
8. evidence_refs用当前报告快照解析成题目/选项/回答编号；不能链接到不公开的外部来源。
9. 下载使用 `GET /api/projects/{project_id}/report.md`；不是点击后在浏览器里伪造另一份报告。
10. 无报告/无反馈/加载失败各有明确状态，保留刷新按钮。

验收：零样本显示暂无数据和证据不足；加一条反馈后旧报告不变且有提醒；新报告纳入真实数据。C执行T07～T09。
